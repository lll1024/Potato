## 实现与边界

系统指令要求条件齐备、选择互不依赖的必要查询集中在一次响应提出；参数齐备不是独立性的证明。需要前一步结果才能选候选、来源或交通时仍分步骤；先取得实际链接再读正文，确定实际两端及高德坐标后才查交通。同名地点先澄清，复用当前有效条件和资料，不增加凑批次查询，不减少资料及回答细节，不自动追加专项核实。

复用 #74/#75 的执行循环、预算、真实 MCP/HTTP、SQLite、SSE 和 CLI，不增加依赖推断器、预测查询或生产子 agent。网页最多十条、地图最多一条，两侧独立 0.4 秒启动间隔；历史是串行边界，整批结果按提出身份交回。停止、真实退出和保存故障仍先收束在途调用再释放运行名额。

真实 Exa 免费限流返回还可能通过 MCP `_meta.ai.exa/rateLimited=true` 表示，而没有 `isError` 或结构化错误码。本次实测发现原适配器误记为 `malformed`；修复后暂停网页，保留地图和其他真实成功结果，注册及付费指令仅留在原始轨迹，不作为模型操作要求。

## 方法与证据范围

[query_batching_eval.py](../../tests/query_batching_eval.py) 从公开 `/api/turns`、轮次快照和载荷 API 运行真实模型及实际执行链路。地图和网页使用固定 MCP/HTTP 返回，延迟统一为 0.8 秒，实际限速保留 0.4 秒。真实模型沿用本机 `MODEL_ID=gpt-6.1-sol` 及兼容服务；不保存凭据和私有服务地址。旅行时间固定为北京时间 2026-10-14 10:00，旅行要求与资料保持一致，数据库每个场景独立，后续调整在同一会话执行。

每次保存整轮等待、实际模型请求及耗时、用量、工具参数、结果、实际开始和结束、等待/执行耗时、摘要、重试、故障以及完整回答。原始证据位于 [query-batching](query-batching/)，失败与初版证据保留，不能代替最终版本。`wait_ms` 从提交前计至轮次完成，包含最多约 50 毫秒状态轮询误差；工具等待/执行时间的逐条总和不是整轮等待，模型与各批工具的阶段耗时分开计算。

代表性短任务对照统一关闭上下文维护，以单独观察集中查询和工具调度；模型容量、回答额度与单次超时未调整。此配置与本机启用上下文维护的配置有区别，因此不据此声称长会话摘要性能改善。摘要、恢复、输入容量和共享预算由本次公开入口自动回归联合验证，另补测沿用 `.env` 配置的真实模型行为。固定服务资料包含测试域名、控制公交及坐标，不证明真实景点政策、线路或未来天气。

## 并发机制与真实承载

固定序列为三个必要网页搜索和两个地图地点搜索，两个版本使用相同顺序和 0.8 秒服务延迟；模型是固定替身，仅观察机制。改动前五项逐条执行，最终版本网页三个与地图一个重叠、地图逐条推进。工具阶段的重叠来自实际开始/结束记录；不以墙钟阈值作为正确性断言。[基线](query-batching/mechanism-before.json.gz)、[最终](query-batching/mechanism-final.json.gz)保留完整载荷，工具阶段从 **4.108 秒降至 1.657 秒**，包含提交/存储/轮询的整轮约 4.14 秒与 1.69 秒。

公开 Web 的当前回归以阻塞/释放证明网页搜索和正文合计十条、地图一条、跨服务重叠、两侧间隔、名额释放和乱序配对。网页早完成时快照/SSE立即可见，但不提前发下一模型请求，列表不按完成先后重排；历史先收齐前段、按真实余量回读后继续后段。

按最终上限 10 和 0.4 秒间隔，向真实免费 Exa 发出十条独立搜索：[首次](query-batching/live-load.json.gz)峰值 **7 条**在途，九条成功、一条免费限流（修复前误分类）；[复验](query-batching/live-load-repaired.json.gz)十条成功，峰值 **5 条**在途，无限流或失败。配置上限 10 不等于本次实际十条同时在途；没有通过人为延迟制造真实供应商十条在途，也不能据此保证持续十并发安全。未注册、付费、领取额度或改变官方额度。

模型真实行为与质量核对：

- 网页场景一次提出三个独立主题搜索，下一步才按三个实际链接读取正文。三份玩法、90/75/45分钟、私人院落限制、未取得具体街口、来源身份及实际链接均保留。基线已能集中这组搜索，因此没有模型请求减少的证据。
- 混合场景一次提出两份玩法搜索、两个指定地点定位及天气。后续正文与公交集中提出时，链接和两端高德坐标均已取得。两处玩法、90/75分钟、具体地址、公交“控制公交1路”、真实上下车站、30分钟/4.5公里、日期天气、预约入口及未核实状态都保留。七次工具样本把两份正文放进一次多链接读取，实际仍读取同样两份正文，并非少取资料。
- 依赖场景先搜索候选并读取两篇正文，再选择有青铜器专题的首都博物馆、取得它的定位，最后查公交；未提前定位或查询未选博物馆的交通。已指定的玉渊潭定位可与候选正文读取重叠，因为其选择不依赖博物馆候选；公园来源仍搜索后读取。三份必要正文都取得，仍需五次模型请求。
- 调整场景复用已确定地点、坐标、玩法、限制和来源，只查询步行与新日期天气。10月18日、只步行、不安排餐饮、70分钟/4.5公里及小雨影响准确保留，旧公交不再用于当前安排，未重问已知条件或自动追加政策核实。仅调整轮次基线32.65/38.26秒、最终30.63/30.27秒；工具均为两个地图查询，工具阶段都约1.61秒，不能将这部分等待差异归因于网页并发。
- [同名分店补测](query-batching/ambiguous-final-1.json.gz)取得两个真实返回的书店候选后列名称/地址澄清，没有猜选分店或发路线请求；[真实 CLI](query-batching/cli-final-1.json.gz)也一次提出三次搜索、取得链接后读取正文，保留同样玩法与限制，退出码0。

参数核对确认所有正文链接都来自更早模型步骤的实际搜索结果，路线两端来自更早已取得的高德坐标；这只证明参数依赖，不自动证明选择独立。上述独立性结论来自固定旅行要求、候选资料内容、实际批次及回答的逐项人工核对。没有发现来源/坐标编造、已预约承诺、额外核实或必要资料缺失；两组后续调整均保留当前要求。

[逐样本质量核对](query-batching/quality-review.json)关联16份基线/最终证据。另按本机真实配置启用上下文维护、1,000,000容量（公开记录输入预算892,000）补测混合场景：[基线](query-batching/mixed-configured-before.json.gz)47.92秒、3次模型/8次工具，[最终](query-batching/mixed-configured-final.json.gz)42.07秒、3次模型/7次工具，两份正文及全部必要事实均保留，摘要与重试为0。启用配置的[CLI补测](query-batching/cli-configured-final.json.gz)3次真实模型请求、退出码0，搜索与正文依赖及玩法/来源边界也保留；此单次补测不替代重复对照或证明长会话质量。

**机制结论：符合规格，固定序列的工具阶段缩短。真实任务结论：整体改善未得到稳定证明。** 网页任务较短、两轮调整合计也较短；混合平均等待受一次真实模型超时显著拉长，依赖链两次的平均等待也未改善。成功模型步骤数量没有下降，不能声称集中策略已减少模型往返。

混合最终第一次中，实际第二个模型请求等待 **60.006秒后 `APITimeoutError`**，按既有规则重试一次后成功；四次实际模型耗时合计129.464秒，工具阶段约3.31秒。这条失败计入预算和请求消耗，已取得结果保留，未重放工具，慢样本留在最终对照。依赖最终第一次没有重试，但模型耗时63.244秒，高于其基线52.762秒；工具阶段从约6.50秒降至4.13秒，仍不足以抵消模型时延。所有代表性样本摘要均为0，工具故障均为空；成功样本的模型生成时延也明显波动。每组仅两次、采用控制资料且分时运行，不支持显著性或普遍提速结论，不预设收益百分比。
