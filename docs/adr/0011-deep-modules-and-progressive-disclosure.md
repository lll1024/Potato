# 按完整能力组织深模块，并通过公开契约渐进式披露

2026-10-23，用户提出将整个仓库组织为若干职责清晰的深 module，希望只掌握各 module 的公开 interface 即可理解项目整体，并让 Codex 据此按需展开 implementation。用户已逐项确认下述取舍并确认整体理解，设计状态为 accepted；同日调用 to-spec 发布[实施规格 #79](https://github.com/lll1024/Potato/issues/79)，于同日通过 implement #80 进入行为基线与迁移校验阶段。

## 已确认的取舍

顶层 module 优先围绕完整能力组织，允许确有共享职责的技术 module。例如，旅行者偏好的提取、保存和管理共同构成一项能力；其内部可以包含前后端 implementation，并通过明确的公开契约协作。跨前后端不强求只有一个代码入口，具体 module 划分继续依据代码中的职责与耦合确定。

改造允许调整内部目录、导入路径和调用方式，并同步迁移仓库内调用方；现有启动命令、网页行为、已有数据与旅行规划规则保持兼容。相较连内部路径也保持不变，这一选择允许把实现知识收回 module，以提升调用方的 leverage 和维护者的 locality。

渐进式披露采用阅读指引与自动依赖检查：Codex 默认先读仓库总览和任务相关的公开契约，修改内部实现时再展开对应 implementation。自动检查约束跨 module 的代码依赖通过公开 interface；阅读指引负责何时展开资料，两者共同保证契约可依赖。

## 顶层职责地图

用户已确认以下六项作为顶层 module 划分的起点，后续通过状态归属和依赖检查验证是否需要合并或调整。

| module | 对外承担的职责 |
| --- | --- |
| 助手会话 | 提交、轮次运行、停止、历史与执行轨迹查看，包含相关前后端 implementation |
| 旅行规划 | 理解当前旅行要求、执行规划规则、推进模型步骤并形成回答 |
| 资料获取 | 获取地点、餐饮、交通路线、天气和网页资料，管理查询执行 |
| 模型上下文 | 从完整历史构造模型输入，处理压缩、容量与历史回读 |
| 旅行者偏好 | 提取、保存、使用及管理跨会话稳定偏好，包含相关前后端 implementation |
| 本机记录 | 提供持久化、原子提交和记录恢复，作为共享技术 module |

启动装配和模型调用 adapter 先作为支撑 implementation；辅助文件不必各自成为顶层 module。

## 状态归属与共同提交

助手会话掌握提交身份、接受与拒绝、全局运行名额、停止请求和对外状态；旅行规划掌握模型步骤、整轮调用预算、查询推进，以及回答或未完成结果。停止信号传给执行中的规划，实际调用与保存收束后，助手会话才释放名额。Web 与 CLI 继续复用旅行规划，各自的历史保存范围保持现状。

模型上下文统一维护轮内完整协议的追加与模型视图同步。旅行规划交入新消息和工具结果，不分别修改两份状态；模型上下文负责压缩、容量检查和历史回读，本机记录负责完整历史及有效版本的持久保存。旅行日期的解释规则归旅行规划，模型上下文保留已经确定的日期，压缩时不重新解释。

跨 module 的既有共同保存继续保持原子性，包括接受输入与登记偏好待处理记录，以及保存轮次结果与有效上下文版本。本机记录在内部完成事务，各能力通过公开契约提供所需数据和规则；调用方无需获取数据库连接或自行安排提交顺序。共享数据库可以保留，职责划分通过状态归属与 interface 保证。

## 混合批次与规划结果

旅行规划在内部集中协调模型提出的混合调用批次：外部查询分段交给资料获取，历史回读交给模型上下文，整轮预算由旅行规划统一扣账。协调 implementation 隐藏排序、等待与结果拼接，模型步骤接收完整批次结果；资料获取与模型上下文不因批次执行而相互掌握供应商限速或历史分页细节。

旅行规划通过公开 interface 返回结构化规划结果，包含回答、完成状态、终止原因和供共同保存使用的结果数据。调用方无需解析观察事件判断规划是否完成，也无需分别修改完整协议与模型视图。执行轨迹继续在运行过程中逐条记录；执行返回与保存成功分别表达，生成但尚未保存的回答不作为已完成历史。

## 目录与公开入口

每个后端 module 采用独立目录与显式公开导出入口，相关前端 implementation 按同一能力名称归组。内部文件保持私有，跨 module 依赖通过公开入口，并接受自动检查。

用户和 Codex 共用每个 module 的一份公开契约，位于 `docs/modules/`。契约说明能力、真实入口、输入输出、状态归属及失败语义，类型与测试链接到代码，减少重复抄写。公开代码入口链接对应契约；根级 `AGENTS.md` 提供阅读顺序与触发条件，并链接仓库总览，内部说明按需展开。

## 依赖方向、失败语义与检查

用户已确认以下允许的跨 module 依赖，均通过公开 interface：助手会话依赖旅行规划、旅行者偏好和本机记录；旅行规划依赖资料获取和模型上下文；旅行者偏好与模型上下文依赖本机记录。本机记录不反向导入规划或偏好的运行 implementation。执行事实通过装配时注入的记录入口保存，停止与通知通过明确契约传递。

单次查询失败作为查询结果返回，规划可继续使用其他资料。完成、停止、预算耗尽和模型请求失败通过结构化规划结果表达，保留现有状态与原因含义。记录故障使用明确的中止信号，阻止后续调用，等待在途调用真实返回并收束保存尝试，由助手会话展示未保存状态；调用方不解析错误文案判断这些情况。

自动检查覆盖公开导出、跨 module 导入路径及依赖图无环。生产代码跨 module 只使用公开入口；调用方测试及跨 module 行为测试通过公开 interface 验证；module 自身的内部测试可以使用明确归属的内部 seam。启动装配与必要共享支撑设明确规则，旧测试迁移时保留行为覆盖。

## 公开 interface 的形状

用户已确认采用“主流程集中、独立操作明确”的形状。比较过最少入口、能力句柄与分步组合、面向常用流程三种方案后，选择集中主流程，同时保留真实独立操作，以减少调用顺序知识。方法数量不作为 depth 指标，完整契约须说明操作、不变量与失败语义。

| module | 公开操作的形状 |
| --- | --- |
| 助手会话 | 提交、核对接受结果、停止、状态、历史与轨迹读取、改名、删除、通知 |
| 旅行规划 | 一个主要规划入口，返回结构化结果；CLI 的跨轮状态通过不透明的延续凭证传回 |
| 资料获取 | 查询可用能力、执行一段有序外部查询 |
| 模型上下文 | 开始本轮、准备请求、追加响应与工具结果、历史回读、超限恢复、生成保存材料 |
| 旅行者偏好 | 读取、编辑、删除，以及后台处理生命周期 |
| 本机记录 | 原子接受、追加事实、原子完成、一致读取、偏好持久操作与重启恢复 |

具体符号、字段和参数细节留到规格阶段确定。装配只组装公开入口，共享支撑只承载实际复用的基础类型和 adapter。

## 迁移与最终验收

用户已确认按可运行的完整链路逐步迁移：先固定行为基线，落实公开入口与原子记录，贯通一条完整 Web 规划链路，随后扩展覆盖全部能力，逐步收拢上下文、资料获取、规划、会话交互及偏好的内部职责。具体先后关系在任务拆分时确定，每阶段均运行对应回归，并立即检查已迁移代码的依赖；最终覆盖整个仓库、清除迁移期间的临时转发并统一导航。

最终验收组合如下：

- 行为回归：后端测试、类型检查、前端测试与构建，以及关键浏览器和进程恢复场景通过。
- 基线对照：比较模型可见请求、工具结果、终态和旧数据续聊；随机身份与时间等字段按明确规则归一化。
- 独立 Codex 阅读任务：只读总览与契约，解释正常、停止、失败和重启流程，并正确定位修改入口。
- 调用与修改任务：通过公开 interface 使用能力；在临时环境中修改一处内部 implementation，验证调用方及契约测试保持有效。
- 结构检查：公开导出、跨 module 导入和无环依赖检查通过。

阅读任务保留文件访问记录与回答证据，以定位正确、契约足够使用为通过条件；使用 module 的调用方无需协调其私有状态，内部重构后其他 module 的调用方式与契约测试保持有效。文件数量少、文档存在或目录整齐本身不作为达成目标的证明。
